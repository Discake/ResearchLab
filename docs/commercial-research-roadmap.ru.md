# ResearchLab — Дорожная карта прикладных инженерных исследований

> Статус: предложения для развития после MVP · 2026-10-24
> Связанные документы: [Видение](../VISION.ru.md), [Доменная модель](../DOMAIN.ru.md), [Концепция Research Story](research-story-concept.ru.md), [План реализации](../IMPLEMENTATION_PLAN.md).
> Это **не** новые обязательства для M3–M6 без отдельного утверждения.

## Аудитория и позиционирование

ResearchLab предназначен для инженеров, которым нужно **сравнивать технические решения, изучать воспроизводимые данные и обосновывать выводы**. Это независимые разработчики, специалисты R&D и численных методов, backend/performance-команды, embedded/telecom-разработчики и архитекторы, проверяющие PoC.

ResearchLab не заменяет production-мониторинг, CI/CD, продуктовые A/B-тесты, трекеры задач и универсальные BI-системы.

## A — Эталонные запуски и выявление регрессий

- Автор может явно **закрепить один Run как эталонный (baseline)** для конкретного Experiment и контекста сравнения.
- Эталон указывает на точный неизменяемый Run ID, а не на «последний запуск».
- Новые запуски сравниваются с эталоном: абсолютные и относительные изменения, единицы измерения, различия параметров и конфигурации, отсутствующие метрики.
- **Статус Run** (успешность выполнения) отделён от **результата сравнения** (регрессия, улучшение, недостаточно данных).
- Для корректного сравнения важны окружение, набор входных данных, условия, параметры и смысл метрики. Несовпадения подсвечиваются, а не скрываются.
- Изменение выбора эталона создаёт новую версию назначения или запись истории выбора; никогда не переписывает данные прошлых Run и уже экспортированных Publication.
- Позднее: разные эталоны для сценариев/окружений и автоматический поиск регрессий по осмысленным порогам.

**Пример:** Run A закреплён как эталон p95 latency API; Run B и C сравниваются с ним. Успешное завершение B не исключает ухудшения производительности.

## B — Пакетные эксперименты и матрицы параметров

- Формирование ограниченной матрицы допустимых комбинаций параметров и повторных запусков.
- Группировка запусков без утраты их индивидуальных параметров и происхождения.
- Показ прогресса, неудач и сравнения конфигураций.
- Очереди и распределённое выполнение добавляются лишь после MVP локального исполнителя; соблюдаем ограничения ресурсов.

## C — Acceptance Criteria / Quality Gates

- Пользователь определяет критерии, например `p95_latency_ms < 100`, допустимую долю ошибок или максимальную память.
- Оценка только на реальных измерениях с явно заданными единицами, агрегацией и условиями сопоставимости.
- Результат: **Pass / Fail / Inconclusive / Not evaluated**.
- **RunStatus.Succeeded не тождественен прохождению критерия.** Успешно завершившаяся программа может не удовлетворять требованиям, а отсутствие данных не означает успех.
- Критерий, источник данных, расчёт, порог и версия процедуры доступны для просмотра.
- Автоматический quality gate не объявляется математическим или научным доказательством.

## D — Контекст и происхождение эксперимента

- Сохраняем доступные сведения об окружении (ОС, архитектура, runtime/toolchain, оборудование), идентификатор/хеш входных данных, Git SHA, dirty state, конфигурацию, теги и обозначение сценария.
- Показываем известные, неизвестные и потенциально несопоставимые условия.
- Не публикуем секреты, локальные пути и переменные окружения без явного разрешения.
- Позднее улучшаем описание окружения, не обещая точного воспроизведения при недостатке данных.

## E — Technical Decision Report

- Необязательный шаблон Research Story: **Проблема → Альтернативы → Критерии → Методика → Результаты → Риски/затраты → Решение → Ограничения**.
- Ссылки на точные эталонные и сравниваемые Run, метрики, артефакты и Git-версии.
- Описание компромиссов; возможен вывод «недостаточно данных». ResearchLab не выбирает «лучшую» архитектуру без заявленных критериев.
- Отчёты экспортируются как неизменяемые публикации только для чтения.

## Evidence links и быстрая проверка утверждений (сквозная функция)

**Основной сценарий:** читатель видит инженерное утверждение и сразу может проверить данные, которыми автор его подкрепляет или которые ему противоречат.

Предусмотрены два основных способа перехода:
1. **Гиперссылка / якорь:** клик по утверждению или его ссылке переносит к конкретному фрагменту, таблице, графику, Run, сравнению или разделу; якорь можно переслать как прямую ссылку.
2. **Кнопка «Проверить данные»:** открывает контекстную панель/модальное окно без потери позиции чтения, со ссылками на полные первичные данные.
3. **Обратная навигация:** от доказательных данных к утверждениям, которые на них ссылаются.

В контекстной панели читатель должен быстро увидеть:
- Текст утверждения, область применимости и допущения;
- Конкретные ID Run, параметры, Git SHA, предупреждение о dirty tree, окружение и артефакты;
- Метрики, единицы, выборки/агрегацию, сравнение эталона с кандидатом и отсутствие данных;
- Разграничение интерпретации автора и зарегистрированных наблюдений;
- Понятный расчёт, если вывод основан на вычисленной величине;
- Противоречащие или недостаточные свидетельства, а не только подтверждающие.

**Не называть наличие данных автоматическим «доказательством».** Предпочтительны названия «Подтверждающие материалы», «Проверить данные», «Детали проверки». Математическое доказательство, статистическая уверенность, повторяемость бенчмарка и выполнение инженерных требований — разные стандарты подтверждения. Если утверждение помечено как «проверено», нужно сохранить область проверки, критерий, процедуру и того, кто её проводил; статус не означает научной сертификации.

### Иллюстративное представление (не утверждённая схема)

```md
Оптимизированная реализация уменьшила p95 latency при исследованной нагрузке.
{{evidence:comparison-42}}
```

Позднее возможна модель `Claim` + `EvidenceReference` + `EvidenceSet` с привязкой к редакции Story и неизменяемым Run/Artifact. **Не вводим эти сущности в M3/M4 только ради этой идеи.** В раннем M6 хватит явных ссылок и якорей; расширенную панель проверки можно добавить постепенно.

### Целостность публикаций

- Стабильные якоря и прямые ссылки должны работать в статическом экспорте без backend автора.
- В экспорт включаются выбранные доказательные данные и расчёты для проверки; отсутствующие или неразрешённые ссылки обнаруживаются при экспорте.
- Экспортированный снимок и показанное в нём назначение эталона неизменяемы.
- После публикации нельзя подменять Run, эталон или автоматически пересчитывать исторические выводы на новых данных.
- Графики и расчёты строятся по сохранённым реальным измерениям либо явно атрибутированным материалам; фикстуры помечаются.
- Просмотр доказательных данных не открывает публичный доступ к запуску программ.

## Предлагаемая последовательность

| Этап | Объём |
| --- | --- |
| M3–M4 | Новых обязательств нет; сохраняем происхождение Run, неизменяемые метрики/артефакты. |
| M5–M6 | Базовые ссылки на конкретные данные и якоря в Story; простая панель проверки, если недорого. |
| После MVP P1 | Эталонный Run, ручное сравнение и расчёт отклонений, панель проверки утверждений. |
| После MVP P2 | Критерии качества, матрицы параметров, усиленные проверки сопоставимости. |
| После MVP P3 | Расширенные отчёты о технических решениях, производная статистика и командные сценарии. |

## Открытые вопросы

- Область действия эталона: Experiment, сценарий, класс оборудования, набор данных или именованная группа сравнения?
- Какие условия делают два Run сопоставимыми по умолчанию, а какие требуют явного подтверждения?
- Нужно ли делать утверждения отдельными сущностями или достаточно аннотированного Markdown?
- Как показывать противоположные свидетельства и неопределённость?
- Как встраивать данные и вычисленные сводки в компактный статический экспорт?

**Принцип:** быстрая практическая проверка должна быть возможна без превращения приложения в систему формальных математических доказательств, орган научной сертификации или очередной CI/CD.
