# Минимальное локальное исполнение доверенной программы

Реализован синхронный сценарий Application через настоящий адаптер Execution поверх M3.1a.
Это часть M3, а не весь этап.

```csharp
var inspector = new WorkspaceInspector();
var catalog = new ProjectCatalog(store, inspector);
// Импортировать проект/создать Experiment, показать ReviewTaskAsync, затем вызвать
// ConfirmTaskAsync только после одобрения владельца. Сохранить тот же catalog.
var execution = new RunExecution(store, catalog, inspector, new ProcessRunner());
var runId = await execution.StartRunAsync(experimentId, parameters, cancellationToken);
var run = await store.GetRunAsync(runId, cancellationToken);
```

Вызывающий связывает существующие компоненты Application/Infrastructure и
ResearchLab.Execution.ProcessRunner; DI-контейнер, CLI и хост не добавлены.
IProcessRunner принадлежит Application. Execution не зависит от Infrastructure,
не обращается к БД и не меняет доменное состояние. Callback подтверждает реальный старт;
Application сохраняет Running до принятия результата. Если callback завершается ошибкой,
runner останавливает принадлежащий попытке процесс и передаёт ошибку без повторного запуска.

StartRunAsync ждёт завершения и сохранения терминального статуса, затем возвращает RunId.
Это намеренно более простой синхронный сценарий по сравнению с ранним подтверждением
старта из проекта жизненного цикла. Ошибки подготовки/валидации возникают до вставки.
Ошибка старта возвращает ID сохранённого Failed без PID, времени старта и exit code.
Ненулевой код даёт Failed с фактическим exit code; нулевой код и успешное ограниченное
дренирование потоков дают Succeeded. Протокола метрик/артефактов ещё нет; успех не доказывает
научную корректность или наличие ожидаемых измерений.

Снимки используют валидацию/defaults и фабрики Domain. Перед созданием Run выполняется
свежая best-effort инспекция исходников; недоступные сведения Git остаются неизвестными.
Повторно загруженное определение структурно сравнивается с подготовленным. Created
сохраняется до передачи исполнителю; непосредственно перед исполнением доверие повторно
проверяется относительно подготовленного fingerprint. Позднее изменение Experiment не
переписывает Run. Сохранение использует последнюю записанную версию без автоматических
повторов конфликтов или запуска. Ошибки БД передаются вызывающему без заявления о сохранённом исходе.
Исключения самого исполнителя дают Failed с общей диагностикой без выдуманного exit code.
Ошибка подтверждения старта сохраняется как исходная ошибка приложения/БД, даже если
адаптер оборачивает или поглощает её; попытки записать терминальный статус нет.
Ошибка чтения/доступа при финальной проверке доверия переводит Created в Failed без запуска.

Runner использует явный executable, буквальный ArgumentList, UseShellExecute=false и
проверенный workspace. На Windows разрешены только точки входа .exe: .cmd/.bat могут
включать командный процессор даже при UseShellExecute=false. Контракты импорта/review M2
не менялись; неподдерживаемый файл безопасно отклоняется на этапе исполнения. На Unix
действуют права исполнения и разрешение интерпретатора ОС; исполнение на Unix не проверено.
Доверие по-прежнему покрывает входной файл/конфигурацию, а не транзитивные библиотеки,
интерпретаторы и runtime-файлы. Это доверенный локальный код, не песочница ОС; явно
объявленные executable-интерпретаторы остаются кодом, который владелец должен проверить.

Проверенные скалярные параметры передаются JSON-текстом, совместимым с UTF-8, через
RESEARCHLAB_PARAMETERS_JSON без подстановок в команды. Вместо наследования stdin
используется закрытый перенаправленный ввод. stdout/stderr параллельно дренируются
фиксированными буферами, отбрасываются и не сохраняются. Фиксированный общий лимит 1 MiB
останавливает избыточный вывод с Failed. Timeout задачи ограничивает исполнение/дренирование
и после остановки даёт TimedOut. Очистка пытается завершить дерево процессов и ждёт корневой
процесс до пяти секунд; невозможность остановки передаётся ошибкой, без ложного успеха.
Выход и оба потока наблюдаются до ожидания подтверждения старта: завершение, подтверждённое
до deadline, остаётся успешным при медленном callback. Отменённое чтение означает неполную
обработку, а не EOF. Очистка также ограничивает ожидание общей задачи выхода/чтения пятью
секундами, в том числе при исключении во время остановки процесса.

CancellationToken используется только до первоначальной вставки. После сохранения Created
сценарий владеет исполнением и записью состояний до завершения; отмена запроса вызывающего
не реализует CancelRun. Расширенная отмена, фоновое исполнение, сохранение логов, выделение
директории вывода/артефактов, список истории и восстановление после рестарта не реализованы.
Наследуемое окружение не изолируется. Гонки файловой системы TOCTOU и окно сбоя между
стартом ОС и записью Running остаются согласно проекту жизненного цикла. Очистка потомков
после завершения корневого процесса не гарантируется; адаптер не добавляет job objects ОС
или изоляцию процессов.

Тесты используют отдельную синтетическую программу из tests, а не продуктовый CLI или
экспериментальные доказательства. Проверяются реальный SQLite и порядок состояний,
ошибка старта, отсутствие доверия, ошибки параметров, подмена executable, буквальные
аргументы, передача параметров, оба потока вывода, timeout, лимит вывода и очистка при
ошибке callback.
Регрессионные тесты также покрывают исключения исполнителя до/после старта, реальные ошибки
записи SQLite при старте/завершении, медленное подтверждение, ошибку чтения при финальной
проверке доверия, неполный результат и очистку живого дерева с потомком, наследующим оба потока.
