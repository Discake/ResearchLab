# M4.4 — Чтение сохранённых метрик

Из корня репозитория, Windows / PowerShell 7.3+:

```powershell
dotnet build ResearchLab.slnx
pwsh -NoProfile -File ./scripts/metric-smoke.ps1
```

Прочитайте review исполняемого файла, аргументов, параметров и fingerprint в stderr,
затем введите `yes` для доверия этому вызову. Другой ответ или EOF означает отказ
(код 5), Run не создаётся. Скрипт готовит новый приватный временный каталог, импортирует
демонстрационный ProcessFixture, создаёт Experiment, запускает с проверенным `n=2`,
выводит сохранённый Run ID и читает метрики отдельными процессами CLI. Проверяются
значения, имена, повторяющиеся шаги, последовательность и пагинация с фильтром.
Файлы сохраняются для проверки; `-Directory <новый-путь>` задаёт каталог.
Это демонстрационные вычисления, **не benchmark**. Дочерний процесс вычисляет значения
и отправляет настоящие события stdout `@researchlab/v1`; скрипт не вставляет точки в БД.

Для любого сохранённого Run (используйте БД и logs из сохранённого каталога):

```powershell
$cli = './src/ResearchLab.Cli/bin/Debug/net10.0/researchlab.dll'
$common = @('--database', '<retained-root>/research.db', '--data-dir', '<retained-root>/logs')
dotnet $cli @common run metrics <run-id>
dotnet $cli @common run metrics <run-id> --name demo_square --offset 2 --page-size 1
```

JSON выводится в stdout, диагностика — в stderr. Существующие коды: 0 — успех,
2 — неверные аргументы, 3 — неизвестный Run, 4 — недоступное/несовместимое хранилище,
130 — отмена. Известный Run без точек, отсутствующее имя или offset за концом
дают успешный ответ с пустым `points`. Имя сравнивается точно, с учётом регистра.
`run show` не включает историю метрик.

Application предоставляет `IRunMetricReader.GetMetricsAsync(RunId, name?, RunPageRequest?, cancellationToken)`
и неизменяемые DTO `RunMetricPage`, `MetricPointDetails`. SQLite проверяет наличие Run
без загрузки агрегата, проецирует только нужные точки без tracking, не сохраняет данные
и не применяет миграции при чтении. CLI открывает SQLite read-only. Объекты EF и queryable
не выходят за границу. Миграция не нужна: используются существующие индексы
Run/Sequence и Run/Name/Sequence.

По умолчанию страница содержит до 50 точек, максимум — 100; offset неотрицательный.
Фильтрация выполняется до пагинации. Порядок — уникальный `Sequence` приёма в конкретном
`runId`; шаги и timestamps могут повторяться. Необязательные поля сохраняют JSON null.
`recordedAtUtc` — сохранённое время приёма в UTC, не время измерения от дочернего процесса.
Фильтрация не перенумеровывает sequence. `hasMore` проверяется одной дополнительной
строкой; увеличивайте offset на число полученных точек с тем же фильтром. Активный Run
может дописывать данные между запросами: страницы не являются общим замороженным снимком.

Ожидаются `demo_square=(4,4,16)` с шагами `(1,1,2)` и `demo_input=2` без step/unit;
глобальные sequence `(1,2,3,4)`. ID и timestamps меняются. Полный реально полученный
JSON сохранён в [metric-query-actual.json](metric-query-actual.json).
Для команды с фильтром выше ожидаемая и полученная страница содержит только value 16,
step 2, unit `1`, sequence 3, offset 2, pageSize 1, hasMore false.

Проверки: `dotnet build ResearchLab.slnx --no-restore`,
`dotnet test --solution ResearchLab.slnx --no-build`,
`dotnet format ResearchLab.slnx --verify-no-changes --no-restore`.
Тесты покрывают пустые/несколько серий, повторяющиеся шаги, глобальный порядок,
изоляцию Run, неизвестный Run, ограниченные страницы, фильтр, необязательные поля,
новый процесс CLI и неизменность байтов БД после чтения. При автоматической проверке
smoke-test тестовый stdin получает `yes`; сам скрипт не подтверждает доверие автоматически.
Unix не проверен. Графики, артефакты, UI и публикации не добавлены.
