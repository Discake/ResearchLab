# M4.2 — долговременный приём метрик Run

`RunMetricIngestion` — Application-владелец одного уже сохранённого **Running** Run.
Он принимает типизированный `MetricEvent` из M4.1. Разбор stdout, запуск процесса и
изменения M3 не подключены. Асинхронные вызовы выполняются последовательно с await.

## Контракт

- `OpenAsync(store, runId, batchSize, flushInterval, timeProvider)` проверяет Running
  и запоминает сохранённую версию. Размер пакета по умолчанию 128, диапазон 1–128.
- `AcceptAsync(event)` фиксирует время поступления в Application и буферизует событие.
  null означает **буферизацию, а не сохранение или доменное принятие**. Доменная
  проверка происходит при flush. При достижении размера либо истечении интервала
  на очередном событии flush выполняется в том же async-вызове. Интервал по умолчанию
  одна секунда, максимум одна минута.
- `FlushAsync()` вызывает `Run.AddMetric` и атомарно сохраняет все корректные точки.
  Возвращает `SavedCount`, `Version` и ограниченный список отказов: доменный код и
  индекс события с нуля **внутри пакета**. Нужно обрабатывать также результаты
  автоматического flush. Отклонённое событие не расходует Sequence или Version.
  Несовместимые единицы, включая null вместо именованной единицы, не мешают
  сохранению соседних корректных событий.
- `CompleteAsync(ProcessResult)` сначала сохраняет метрики, затем Application выбирает
  Succeeded/Failed/TimedOut/Canceled через существующие доменные переходы. Переходом владеет Application; ProcessRunner не вызывает доменные методы статуса.
  Сохранённые наблюдения остаются при неуспешном исходе и при ошибке terminal-записи.
- Ошибки хранения пробрасываются. `VersionConflict` — `CatalogException`; ошибки SQLite
  сохраняют исходное исключение. После ошибки flush/completion владелец останавливается,
  память остаётся ограниченной, автоматического повтора нет. Перед открытием нового
  владельца нужно явно сверить состояние БД; вычислительную программу автоматически
  не перезапускать. Отмена до помещения в буфер не добавляет событие.
- После успешного завершения владелец также остановлен. Для Created/terminal нельзя
  открыть окно записи. Внешнее завершение, конкурирующее с пакетом, блокирует commit
  проверкой версии. Буферизованные данные ещё не имеют гарантии сохранности.

Фонового writer или таймера нет. Во время отсутствия событий workflow должен явно
вызывать `FlushAsync`, если требуется ограничение задержки по времени: проверка
интервала на поступлении не обеспечивает flush во время простоя. В конце сбора
обязателен flush/complete. Авария может потерять текущий пакет; долговременны только
успешные commit.

## Persistence и стоимость

Существующий `SaveRunAsync` загружает все N сохранённых точек, сравнивает неизменяемый
префикс и присоединяет полный агрегат. Один save требует O(N+B) памяти, чтения и
сравнения. Частые небольшие save могут суммарно давать O(N²) работы с историей.
Семантика M3 сохранена; новый путь метрик этот метод не вызывает.

Минимальное расширение `IResearchStore.OpenRunMetricWriteAsync` возвращает disposable
unit of work с **тем же Run aggregate**, без второй модели жизненного цикла.
Infrastructure загружает скалярное состояние Run, MAX(Sequence) и первую сохранённую
единицу каждой серии текущего пакета. Только Application вызывает `Run.AddMetric` и
методы переходов, затем `SaveAsync`. Внутреннее persistence-окно Run восстанавливает
базовые sequence/единицы; `Metrics` содержит только новые точки, ограничен 128 точками
и не может передаваться обычному `SaveRunAsync`. `GetRunAsync` по-прежнему возвращает
полную историю.

Память O(B), независимо от общего числа наблюдений **и общего числа серий**:
максимум B=128 ожидающих событий и B единиц серий. При K разных именах в пакете flush
выполняет запросы скалярного состояния/максимума, K индексных поисков единиц, B INSERT
и один UPDATE Run. Новый индекс `(RunId, Name, Sequence)` обслуживает поиск единиц;
существующий уникальный `(RunId, Sequence)` — максимум и уникальность порядка.
Стоимость поиска примерно O((K+1) log N), доменных проверок внутри ограниченного
пакета O(B²), плюс вставки и UPDATE. Это анализ стоимости, не измерение throughput.
Нет материализации неограниченной истории, общего кэша серий, worker, broker или
внешней БД. Миграция `MetricSeriesLookup` только добавляет индекс, не меняя наблюдения.

Tracked UPDATE Run проверяет загруженную Version как optimistic concurrency token.
EF SaveChanges сохраняет INSERT и UPDATE одной транзакцией либо откатывает всё.
Побеждает один конкурент; устаревшая запись метрик или terminal завершается ошибкой,
включая конкуренцию с обычным SaveRunAsync. Нарушение уникальности переводится в
VersionConflict только при подтверждённом изменении версии Run в БД; остальные ошибки
остаются ошибками хранения.

Каждая корректная точка увеличивает Version через AddMetric на один. Terminal-переход
добавляет ещё один. Пакет B точек переводит V в V+B, а не добавляет единицу за flush.
Sequence независимо увеличивается на каждую корректную точку. Окно никогда не
присоединяет и не обновляет старые точки. Финальный commit статуса отделён от commit
метрик, поэтому при его отказе уже записанные наблюдения сохраняются.

## Проверки и граница интеграции

`RunMetricIngestionTests` использует реальные временные SQLite-файлы: путь из парсера,
повторное открытие, серии/повторные step/time, отказ по единицам, неуспешные исходы,
read-only отказ, триггеры для отката пакета и отказа terminal, конкурирующие версии,
ограниченные окна и flush по интервалу/размеру/явному вызову. Данные синтетические.

M4.3 подключает настоящий ProcessRunner: последовательный stdout с backpressure,
барьер сохранения Running, ограниченная диагностика и финальный flush перед terminal.
RunExecution передаёт владение метриками/terminal ingestion и сохраняет исходные
ошибки callback. См. [структурированное исполнение](structured-execution.ru.md).
Idle flush, replay буферизованных событий после аварии и постраничное чтение истории остаются за рамками этапа.

## Проверки M4.2 — 2026-10-25

Финальные команды успешно выполнены в текущем Windows workspace:

```text
dotnet build ResearchLab.slnx --no-restore
dotnet test --solution ResearchLab.slnx --no-build --no-restore
dotnet format ResearchLab.slnx --verify-no-changes --no-restore
dotnet ef migrations has-pending-model-changes --project src/ResearchLab.Infrastructure --no-build
git diff --check
```

Сборка: ноль предупреждений/ошибок. Тесты: **389 успешно, без ошибок и пропусков**,
включая **25 новых проверок ingestion**; финальный полный прогон занял 1 мин 21 с.
EF не обнаружил несохранённых изменений модели. Первые 20 проверок ingestion также
прошли отдельно командой:
`dotnet test --project tests/ResearchLab.IntegrationTests --no-build -- --filter-class ResearchLab.IntegrationTests.RunMetricIngestionTests`.

Предварительные попытки: build/test/format внутри sandbox не прошли из-за недоступных
named pipes build-host/testing, затем успешно выполнены вне sandbox. Первый полный
прогон: 388/389 успешно; проверка количества миграций ожидала две вместо трёх. Ожидание
обновлено, весь набор выполнен повторно. Format сначала нашёл смешанные окончания
