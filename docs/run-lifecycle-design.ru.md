# Жизненный цикл Run и взаимодействие с исполнителем — проект

Обновление реализации: владение foreground-исполнением и отмена теперь описаны в
[управляемой отмене](managed-cancellation.ru.md). Этот контракт возвращает попытку,
принадлежащую вызывающему, и сохраняет foreground-driver вместо предложенного ниже
сервиса/API асинхронного старта. Остальной проект восстановления ниже ещё не реализован.

Область: проектирование после M3.1a, не реализованная функциональность и не разрешение
реализовать весь M3. Переходы Domain, контракты M0–M2 и PreparedRun остаются прежними.
CLI, HTTP/UI, управление процессами, фоновый планировщик и зависимости не добавляются.

## Ответственность слоёв

| Слой | Ответственность |
| --- | --- |
| Domain | Параметры/defaults, неизменяемые снимки Run, условия переходов, время и версия агрегата |
| Application | Подготовка, доверие, создание/сохранение Run, последовательная обработка фактов, выбор результата, запросы и решения о восстановлении |
| Infrastructure | Существующий SQLite store, проверка конфигурации/путей/содержимого и best-effort сведения об исходниках |
| Будущий Execution-адаптер | Факты запуска ОС, ограниченный сбор stdout/stderr, факт завершения и подтверждение запрошенной остановки |

Будущий контракт исполнителя принадлежит Application, реализация — Execution. Создавать
его следует при реализации исполнителя. Он получает типизированные данные запуска,
сообщает факты и не получает изменяемый Run или IResearchStore. Вывод дочерней программы
не может задавать PID, состояние Run или успешность валидации результатов. Если потребуется
расширенный сбор метаданных ОС/окружения, его можно разместить в существующей границе
инспекции; чтение ОС/архитектуры средствами BCL в M3.1a не требует новой абстракции.

## Предлагаемые операции

Имена ниже описывают будущие операции; новые публичные API не добавлены.

| Операция | Контракт |
| --- | --- |
| `PrepareAsync(experimentId, parameters)` | Существующая M3.1a: неизменяемые данные без записи Run и исполнения |
| `StartRunAsync(experimentId, parameters)` | Явное действие владельца; свежая подготовка, сохранённый Created, одна попытка запуска; возвращает RunId после подтверждения старта либо сохранения ошибки старта |
| `CancelRunAsync(runId)` | Запрос отмены принадлежащей сервису попытки; принятие запроса отличается от сохранённого Canceled |
| `GetRunAsync(runId)` | Чтение сохранённого состояния; отсутствующий ID — существующая семантика RunNotFound |
| `ListRunsAsync(experimentId)` | Будущее чтение с детерминированным порядком и ограниченной пагинацией; поддержки в store пока нет |
| Сверка при старте сервиса | Обработка запусков предыдущей сессии сервиса, а не активных запусков текущей; не публичная команда исполнения |

Ошибки подготовки, поиска, доверия и параметров возникают до создания Run. После сохранения
Created известная ошибка старта фиксируется на этом Run; возвращается ID с сохранённым
Failed, чтобы диагностика оставалась доступной. Если ошибка хранилища мешает сохранить
результат, операция сообщает сбой и не заявляет успешного перехода.
Повторный StartRun — новая попытка с новым ID, без автоматического повторения запуска.
Неопределённый ответ следует разрешать чтением известного RunId, а не скрытым новым запуском.

## Порядок старта и граница снимка

1. Вызвать существующий RunPreparation с тем же ProjectCatalog, в котором хранится доверие
   сессии. Использовать валидацию Domain; не подставлять параметры в аргументы команд.
2. До создания Run собрать доступные сведения об исходниках/окружении. M3.1a намеренно
   возвращает неизвестное происхождение. Будущий этап исполнения сможет использовать
   Git-инспекцию M2 в рамках разрешённых этому этапу процессов. Не выдавать Git-состояние
   при импорте за состояние при запуске. Неизвестные поля и диагностика остаются явными;
   наблюдение не является атомарным снимком рабочего дерева.
3. Повторно загрузить Experiment и Project. Структурно сравнить определение со снимком,
   включая ограничения/defaults/allowed values, проверить принадлежность проекту и workspace.
   При изменении отклонить попытку с предлагаемой ошибкой PreparationChanged; новая подготовка
   требует явной новой попытки. Нельзя незаметно заменить снимок свежим определением.
   Токена ревизии Experiment в текущем хранилище нет: сравнение структурное, не по ссылке
   и не через Run.Version.
4. Использовать существующий Run.Create с совпадающим Experiment, подготовленными задачей/
   параметрами и собранными метаданными, затем AddRunAsync. Повторная доменная валидация
   здесь намеренна. Ошибки времён отклоняет Domain; нельзя выдумывать будущее время создания
   для обхода проверки. С этого момента входные данные в БД неизменяемы.
5. При будущей реализации выделить отдельную выходную директорию Run в управляемом приложением
   хранилище через файловый адаптер. Проверять принадлежность и ссылки; не брать путь из вывода
   задачи. Ошибка выделения после сохранения переводит Created → Failed.
6. Под контролем владельца попытки непосредственно перед передачей исполнителю снова вызвать
   GetTrustedTaskAsync. Сравнить fingerprint, разрешённый путь executable и значения задачи
   с PreparedRun. Даже заново подтверждённый другой executable не может заменить подготовленный.
   Отсутствие доверия или несовпадение запрещает старт и фиксирует Created → Failed с диагностикой.
7. Передать исполнителю RunId, проверенный путь executable, рабочую директорию, буквальный
   список аргументов, копию типизированных параметров, выходную директорию и timeout.
   Лимиты вывода задаются явной политикой хоста; новые поля конфигурации сейчас не вводятся.
   Кодировка транспорта параметров/выходной директории относится к этапу протокола.
8. Исполнитель сообщает либо ошибку старта без идентификатора процесса, либо подтверждённый
   старт с положительным PID и временем наблюдения. Только второй факт разрешает Run.Start
   и сохранение Running. Обработка завершения ждёт подтверждения этого сохранения.

Повторная проверка доверия — политика Application с инспекцией Infrastructure. PreparedRun
не становится разрешением на многократный запуск. Все пути исполнения должны проходить эту
проверку. Подмена файлов между проверкой и открытием ОС остаётся ограничением TOCTOU
локальной однопользовательской модели; это не гарантия песочницы ОС.

Новая перегрузка фабрики Run для этой последовательности не нужна: совпадение повторно
загруженного определения позволяет существующей фабрике зафиксировать нужные значения.
Редактирование Experiment после сохранения Run допустимо и не меняет сохранённые снимки.

## Факты исполнителя и переходы

Нужны небольшое типизированное подтверждение старта и итог, а не универсальная шина событий.
У попытки один владелец и упорядоченная доставка: подтверждение старта сохраняется до обработки
завершения. Сообщения содержат RunId и принимаются только от владеющей сессии. Удалённые
leases, долговечная очередь и протокол произвольных событий жизненного цикла из stdout не нужны.

| Подтверждённый факт | Действие Domain |
| --- | --- |
| Процесс ОС не запускался; ошибка старта | Created → Failed через Fail(reason), без PID/времени старта/exit code |
| Отмена принята до попытки старта | Created → Canceled |
| Процесс ОС запущен, известны PID/время | Created → Running через Start |
| Exit zero, обязательный сбор и валидация успешно завершены | Running → Succeeded через Succeed(0, true) |
| Ненулевой exit code или критическая ошибка сбора/валидации | Running → Failed с известным exit code и причиной |
| Явная отмена выиграла арбитраж, остановка и сбор завершены | Running → Canceled |
| Deadline выиграл арбитраж, остановка и сбор завершены | Running → TimedOut; Domain проверяет истечение timeout |
| Предыдущий владелец исполнения завершился без сохранённого итога | Устаревший Running → Interrupted с причиной восстановления |

Exit zero сам по себе не доказывает Succeeded. Application определяет resultsValidated
по фактическому обязательному сбору, а не утверждениям дочерней программы. В M3 протокола
метрик ещё нет: нельзя выдумывать измерения или преждевременно реализовывать M4. Когда
появится приём доказательств, принятые данные нужно дочитать, проверить и сохранить до
терминального перехода; текущий Domain разрешает добавлять метрики только в Running.

Запрос отмены и достижение deadline — намерения управления, а не доказательство остановки.
Их обработка последовательна со стартом/завершением конкретного Run. Если отмена пришла
во время запуска ОС, нужно дождаться факта: либо процесса не было, либо сохранить Running
и дождаться подтверждённой остановки. Нельзя фиксировать Canceled, пока принадлежащий
попытке процесс ещё может работать. Если первым принято обычное завершение, поздние
cancel/timeout не меняют его исход; если первой принята отмена/timeout, поздний exit
подтверждает завершение этой причины. Терминальный статус сохраняется ровно один раз.
Текущий Domain не сохраняет exit code при Cancel/TimeOut; менять это правило или обещать
наличие такого кода нельзя.

CancellationToken вызывающего управляет подготовкой/ожиданием, а не долговечной отменой Run.
После вставки отключение клиента не должно лишать попытку владельца или отменять необходимое
сохранение статуса. Явный CancelRun — отдельная операция; остановка сервиса и сбой БД
обрабатываются через владение/восстановление, без выдуманной отмены.

## Сохранение, дубликаты и окна отказа

Для изменения загрузить Run, запомнить сохранённую версию V, вызвать Domain с текущей
версией агрегата, затем SaveRunAsync(run, V). При пакетировании нескольких доменных изменений
V остаётся последней сохранённой версией. Оптимистический UPDATE/транзакция store защищает
от других писателей; будущий внутрипроцессный координатор Run дополнительно сериализует
управление и факты исполнителя. Нельзя держать транзакцию SQLite во время старта ОС/ожидания.

При VersionConflict загрузить победившее состояние. Уже сохранённый идентичный факт можно
подтвердить без изменения; противоречивые или непроверяемые дубликаты дают диагностику без
перезаписи. Одного совпадения PID недостаточно для идентификации попытки. Нельзя вслепую
повторять переход или запуск процесса. Терминальные Run неизменяемы, даже если позднее
сообщение утверждает другой исход. Идемпотентное подтверждение при необходимости относится
к Application; повторные терминальные переходы Domain по-прежнему отклоняет.

| Окно отказа | Необходимое поведение |
| --- | --- |
| До надёжного сохранения Created | Не запускать процесс |
| После Created, достоверно известно, что старта не было | Сохранить Failed старта либо Canceled при явно принятой отмене до старта |
| Процесс существует, сохранение Running не удалось | Сохранить владение; будущий исполнитель должен остановить/дособрать принадлежащий процесс и сообщить ошибку хранения. Не записывать exit code на Created и не утверждать, что старта не было |
| Устаревший сохранённый Running после потери владельца | Перевести в Interrupted без автоматического перезапуска; сохранить снимки и доказательства |
| Сбой между стартом ОС и сохранением Running | Created неоднозначен; нельзя перезапускать или заключать, что процесса не было |
| Итог наблюдался, сохранение не удалось | Удерживать наблюдённый итог, пока жив владелец, сообщить сбой хранения; после рестарта нельзя выдумывать потерянный успех |

Окно между стартом и записью Running нельзя закрыть текущими полями Run: PID сохраняется
только вместе с Running, а Created → Interrupted запрещён. Для автоматического разрешения
неоднозначного Created отдельно потребуются долговечная запись намерения запуска/владения
и надёжная идентификация процесса либо явное ручное разрешение с честной диагностикой.
Этот проект не вводит такой механизм, не меняет автомат состояний, не завершает процессы
по устаревшему PID и не обещает exactly-once execution. Выборка для восстановления,
метаданные владения и подтверждения запуска — нерешённые условия безопасной реализации
полного восстановления M3.

## План проверки будущей реализации

Application проверяется детерминированным fake-исполнителем; реальные процессы — на будущем
этапе Execution. Необходимы следующие проверки:

- Created сохранён до передачи исполнителю; ошибки подготовки не создают Run и не запускают процесс.
- Изменённое определение отклоняется, повторная загрузка совпадающего работает; defaults принадлежат Domain.
- Новый fingerprint, отсутствие доверия или небезопасные пути запрещают передачу даже после подготовки.
- Ошибка старта не проходит через Running; быстрое завершение ждёт сохранения Running.
- Exit zero при ошибке сбора даёт Failed; диагностика и корректные доказательства сохраняются.
- Порядки cancel/start, cancel/exit и timeout/exit дают один обоснованный терминальный статус.
- Конфликты версий и дубликаты не переписывают терминальные исходы и не запускают повторный процесс.
- Отмена токена запроса после вставки не прекращает владение и необходимое сохранение.
- Сбои хранилища и рестарт описываются честно; неоднозначный Created не запускается заново.
- Снимки подготовки/Run неизменяемы; произвольные lifecycle-сообщения и пути от дочерней программы
  не обходят границу доверия Application/Infrastructure.

Изменена только документация. Новые тесты для неё не требуются; перечисленные случаи —
критерии будущего кода, а не заявление о наличии реализованного поведения.
