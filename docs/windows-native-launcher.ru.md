# M3.7b — отдельный Windows native launcher

`WindowsNativeProcessLauncher` — внутренний компонент Execution. В M3.7b он появился
отдельно; M3.7c подключает его к ProcessRunner/CLI с [ожиданием группы](windows-group-lifecycle.ru.md).
Domain, Application lifecycle, recovery и SQLite не меняются. Эта страница описывает
низкоуровневый запуск/владение ресурсами, а не полный lifecycle runner.

## Контракт запуска

Вызывающий передаёт уже проверенный абсолютный путь `.exe`, буквальные аргументы,
проверенный workspace CWD, сериализованный JSON параметров и выделенный абсолютный
каталог результатов. Launcher не повторяет проверку доверия каталога или containment
файловой системы, не ищет программу в PATH и не использует shell. `lpApplicationName`
задан явно, командная строка — изменяемый Unicode-буфер. Окружение наследуется и
сортируется без учёта регистра в Unicode block с двумя завершающими NUL; заменяются
только `RESEARCHLAB_PARAMETERS_JSON` и `RESEARCHLAB_OUTPUT_DIR`.

Экранирование соответствует правилам Microsoft CRT/.NET для кавычек и обратных слэшей,
включая пустые аргументы и завершающие слэши. Это проверяется реальным .NET apphost с
Unicode и JSON; произвольный executable может использовать другой парсер. NUL и слишком
длинная командная строка отклоняются до создания процесса.

Перед каждым запуском создаётся отдельный безымянный ненаследуемый Job только с
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, без разрешений breakaway. `CreateProcessW`
получает `STARTUPINFOEX`, `PROC_THREAD_ATTRIBUTE_JOB_LIST` и
`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. Последний содержит ровно дочерние stdin/stdout/stderr
и требует `bInheritHandles=true`. Назначения после старта и fallback нет. Ошибка подготовки
Job, неподдерживаемые атрибуты, ограничения вложенных Job окружения или ошибка CreateProcess
не допускают запуск. Необязательный внутренний callback инспекции подготовленного Job нужен
тестам для наблюдения handle и провоцирования настоящей ошибки подготовки Win32.

stdin получает EOF после закрытия родительского write end при возврате. stdout/stderr —
раздельные байтовые потоки с ненаследуемыми overlapped read handles именованных каналов.
Временные имена случайны, доступ ограничен текущим пользователем. Ожидающее чтение
поддерживает отмену. Кодировку определяют программа/читатель; синтетический fixture явно
пишет UTF-8. Вызывающий обязан параллельно дренировать оба потока и ограничивать время/объём.

## Владение ресурсами

Владелец и пустые SafeHandles процесса/потока выделяются до CreateProcess. После успеха
handles и PID немедленно передаются владельцу; далее нет проверок членства, callbacks или
потенциально ошибочной managed-подготовки. Handle основного потока закрывается сразу.
Временные дочерние ends каналов, stdin writer, attribute list и environment buffer
освобождаются после создания. Память значений атрибутов сохраняется до
DeleteProcThreadAttributeList, handles живы на протяжении использования списка.
При частичной ошибке освобождаются все уже выделенные ресурсы.

`WindowsNativeProcess` сохраняет Job/process handles и оба родительских потока.
`WaitForRootExitAsync(token)` опрашивает собственный process handle без блокировки worker,
подтверждает signaled-состояние и читает настоящий exit code, включая 259. Отмена завершает
только ожидание и сохраняет владение. Выход потомков и EOF этим не подтверждаются.
Dispose закрывает Job, запрашивая завершение оставшихся процессов, и освобождает handles
и потоки; он **не ожидает и не подтверждает** завершение группы. Жизненным циклом управляет
один вызывающий: Dispose не должен конкурировать с ожиданиями/чтениями; чтения сначала
следует отменить и дождаться их завершения.

Конкурентные запуски компонента используют отдельные явные списки handles. Это не
координирует посторонний код хоста с неограниченным наследованием: одновременный legacy
CreateProcess может унаследовать временно наследуемые дочерние ends каналов. Job handle
никогда не наследуется. Доверенный локальный код сохраняет доступ к файлам пользователя
и правам ОС; containment процессов не является security sandbox.

## Проверки и следующий этап

Windows integration tests покрывают успех, ненулевой код и 259; путь с пробелами/Unicode;
аргументы, замену и наследование окружения, CWD, закрытый stdin; раздельные большие потоки;
отмену чтения/ожидания; членство в конкретном Job, flags и ненаследование; реальную ошибку
подготовки Job и ошибку запуска неверного PE; независимость конкурентных запусков и EOF;
счётчик handles отдельного владельца после повторных ошибок и конкурентных успешных запусков.
Готовность подтверждается с ограниченным ожиданием. Crash gate убивает только отдельного
тестового владельца и подтверждает завершение удерживаемого корня **и потомка**. Очистка
затрагивает только явно созданные тестовые процессы. Вне Windows тесты явно пропускаются.
Проверена Windows x64; x86/ARM64 и другие поддерживаемые версии Windows требуют своих прогонов.

```powershell
dotnet build ResearchLab.slnx --no-restore
dotnet test --project tests/ResearchLab.IntegrationTests --no-build -- --filter-class ResearchLab.IntegrationTests.WindowsNativeLauncherTests
dotnet test --solution ResearchLab.slnx --no-build
dotnet format ResearchLab.slnx --no-restore --verify-no-changes
```

Контрольная точка M3.7b, 2026-10-25, Windows x64 / .NET 10: сборка без предупреждений/ошибок;
8/8 native-launch тестов и 267/267 тестов solution прошли без пропусков; проверка
форматирования прошла. Первая попытка в sandbox завершилась ошибкой IPC pipe тестового
runner до запуска тестов; успешные прогоны выполнялись вне этого sandbox.

M3.7c реализует [ожидание группы и рабочую интеграцию](windows-group-lifecycle.ru.md).
Выход корня, закрытие Job и EOF остаются отдельными свидетельствами; прямой вызывающий
не должен путать низкоуровневое ожидание корня с барьером завершения группы runner.
