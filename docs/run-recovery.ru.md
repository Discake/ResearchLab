# M3.3 — локальное восстановление Run

M3.3 реализует явный foreground-вызов `RunRecovery.RecoverAsync`. Его можно вызывать при
открытии локального хранилища или по решению владельца для согласования оставшихся попыток.
Другие экземпляры ResearchLab могут продолжать исполнение. Нет daemon, планировщика,
распределённых блокировок, опроса процессов, heartbeat, очереди или RPC. Recovery не запускает,
не возобновляет и не завершает дочерние процессы; PID и возраст записи не определяют исход.

```csharp
var store = new SqliteResearchStore(databasePath);
await store.InitializeAsync(cancellationToken);
var result = await new RunRecovery(store).RecoverAsync(cancellationToken);
// result.Recovered: сохранённые переходы в Interrupted
// result.Conflicts: другой писатель победил, Run ещё не терминальный; явный повтор позже
// result.UnverifiedSessions: активные/занятые recovery сеансы или непроверенные свидетельства
```

## Минимальная идентификация и время жизни владельца

Сеанс — **один принадлежащий вызывающему foreground-объект RunOperation**, а не долгоживущий
процесс хоста. У него новый случайный GUID и отдельный файл
`<абсолютный путь БД>.sessions/<sessionId:N>.session`. До вставки Created SQLite-вариант
RunExecution создаёт файл через `CreateNew`, записывает версионированный маркер с GUID,
сбрасывает его на диск и удерживает открытым с `FileShare.None`.
`OwnerSessionId` записывается в ту же строку Runs тем же INSERT, что и Created.
Окна с сохранённым принадлежащим сеансу Run без ID владельца нет. Отдельная таблица сеансов
или эвристика PID/времени старта не нужны. Неизменяемый технический ID владельца не входит
в доменные снимки входов/исходников и не меняется при SaveRunAsync.

Файл эксклюзивно открыт во время передачи подготовки, старта, подтверждения Running,
исполнения, очистки и терминального сохранения. Отмена ожидания вызывающего не освобождает
его. При `ProcessCleanupException` он сохраняется между явными повторами очистки.
Завершение попытки или обычная ошибка после подтверждённой очистки освобождают файл;
если ошибка хранения оставила Created/Running, завершённый сеанс также можно восстановить.
RunOperation.Dispose запрещает освобождать активную попытку или попытку с неподтверждённой
очисткой. Dispose ещё не запущенной операции освобождает сеанс и навсегда запрещает её запуск;
оставшийся Created затем может стать Interrupted. Штатно завершённый driver освобождает
сеанс автоматически. Ошибка вставки/фабрики также освобождает файл.

При аварии хоста ОС освобождает открытый дескриптор. Новый процесс может эксклюзивно открыть
**существующий соответствующий** файл сеанса: по этому протоколу исходный сеанс больше
не владеет им. ID/файлы сеансов не используются повторно и не открываются для нового
исполнения. Recovery удерживает эксклюзивный дескриптор при чтении и сохранении, поэтому
второй recovery не может одновременно захватить тот же сеанс. Файлы намеренно сохраняются;
удаление или сборка мусора для них в M3.3 не реализованы.

## Восстановление и конкуренция

1. Выбрать различные ненулевые OwnerSessionId записей Created/Running с новым составным
   индексом OwnerSessionId/Status. Терминальные записи исключаются до обработки.
2. Эксклюзивно открыть существующий файл и проверить точный маркер. Конфликт доступа,
   отсутствующий файл, неверный маркер, ошибка прав или reparse point оставляют сеанс
   непроверенным. Recovery не создаёт отсутствующие свидетельства. Занятость или отсутствие
   файла не означают аварии. Старые неизвестные владельцы остаются без изменений.
3. Удерживая захват, выбрать ID незавершённых Run сеанса, загрузить каждый агрегат с метриками,
   повторно проверить статус, запомнить версию V и вызвать Domain.Interrupt(now, reason, V).
4. Сохранить с V через существующий оптимистический UPDATE. Побеждает единственная
   терминальная версия. При VersionConflict перечитать победителя: терминальный результат
   не менять, оставшийся незавершённым Run вернуть в Conflicts без слепого повтора по
   изменившимся доказательствам.
5. Освобождать захват и при отмене/ошибках хранения. Предыдущие успешные переходы остаются
   сохранёнными; следующий recovery продолжит остаток. Транзакция БД не удерживается при
   ожидании ОС/файлов. Обычные ошибки хранения/домена передаются вызывающему; часы, ушедшие
   назад за последний переход, отклоняет Domain без подстановки выдуманного времени.

Диагностика Interrupted содержит GUID сеанса, отсутствие терминального результата,
использованные свидетельства владения и явное указание, что остановка ребёнка неизвестна.
Приватные пути в неё не записываются. Снимки, метрики, логи, PID и время старта сохраняются.
ExitCode неизвестен. FinishedAtUtc — **время наблюдения при recovery**, а не объявленное
время выхода процесса; Duration восстановленного Running включает ненаблюдавшийся интервал
и не должен трактоваться как измеренная длительность исполнения.

Минимальное изменение Domain — Created → Interrupted. Created означает отсутствие надёжно
сохранённого подтверждения старта, а не доказанное отсутствие процесса ОС. Владелец может
упасть до запуска, между запуском и сохранением Running либо при обработке ошибки записи
старта. Interrupted фиксирует потерю владения во всех случаях без выдуманных данных старта,
кода выхода, успеха или отмены. Running → Interrupted и финальность терминальных состояний
не меняются. Изменение отражено в DOMAIN.md и DOMAIN.ru.md.

## Гарантии без daemon

Согласование произойдёт **при явном вызове** recovery; самостоятельных пробуждений нет.
Фиксируется подтверждённая потеря владельца исполнения, а не успешная очистка его детей.
Осиротевший subprocess может пережить аварию хоста. M3.3 намеренно не посылает сигнал по
сохранённому PID: повторное использование PID и неизвестное состояние потомков не навредят
постороннему процессу. Активный чужой сеанс защищён эксклюзивным дескриптором независимо
от возраста Run. Не обещаются точное время выхода, потерянный результат, exactly-once
execution или автоматический повтор. Неоднозначность старта классифицируется как Interrupted;
идентификация/остановка детей и сохранение незаписанных данных при аварии — отдельные
будущие задачи.

Доказательство требует доверенного локального хранилища и одинакового абсолютного пути БД
и каталога сеансов у всех экземпляров. Перемещение/копирование живой БД, hard-link-псевдонимы,
сетевые файловые системы и ручная подмена/удаление файлов сеансов находятся вне контракта.
В существующих компонентах пути запрещены ссылки/reparse points, включая БД и каталог сеансов;
конкурентная подмена файлов остаётся локальным ограничением TOCTOU. Хост должен защищать
каталог от дочерних задач и других писателей. Отсутствующий каталог консервативно пропускается.
Файловое владение не является аутентификацией или песочницей процессов ОС.

Nullable-миграция оставляет все строки до M3.3/прямых вызовов AddRunAsync без владельца;
автоматически восстанавливать их нельзя. SQLite-вариант RunExecution регистрирует владение
автоматически. Иные IResearchStore без IRunSessionStore сохраняют совместимость, но создают
непринадлежащие сеансу попытки без автоматического recovery. Восстановлению нужна поддержка
сеансов в том же store. Старые данные не заполняются выдуманными владельцами.

## Проверка

Синтетические тесты покрывают recovery Created/Running, живой второй процесс владельца
и его принудительное завершение, неизменность всех терминальных состояний, повторное и
параллельное recovery, конкурирующий захват, отсутствующие/испорченные свидетельства,
конкурентные терминальные и метрические обновления, сохранность снимков/данных, удержание
сеанса после отмены ожидания и ошибки очистки. Dispose незапущенной операции проверяется
на запрет последующего старта. Также проверяются повторные миграции и nullable-владение
старых записей. Проверена Windows; исполнение/файловое владение Unix здесь не проверены.

M3.6 предоставляет сценарий командой `run recover`; см. [вывод CLI и ограничения](local-run-completion.ru.md).
