# Управляемая отмена локальных Run в foreground

Это реализованный контракт Application/Execution, дополняющий
[проект жизненного цикла](run-lifecycle-design.ru.md). Доменные переходы и схема БД
не изменены. Нет daemon, очереди, detached-выполнения, RPC или отмены из другого процесса.
Вызывающая сторона хранит один `RunOperation` для каждой попытки. [Foreground CLI](foreground-run.ru.md)
теперь использует этот контракт, включая Ctrl+C. Его foreground-повторы очистки сохраняют
того же владельца; сам адаптер Execution по-прежнему не запускает цикл автоматических повторов.

## Владение и ожидание

```csharp
var operation = await execution.PrepareRunAsync(experimentId, parameters, preparationToken);
var driver = operation.ExecuteAsync(); // Сохранить foreground-задачу и обязательно дождаться её.
try
{
    await operation.WaitAsync(requestToken);
}
catch (OperationCanceledException) when (requestToken.IsCancellationRequested)
{
    // Прервалось только ожидание. operation и driver продолжают владеть процессом.
}
// Явное действие владельца; подходит и для будущего foreground-обработчика Ctrl+C:
operation.RequestCancellation();
try
{
    await driver;
}
catch (ProcessCleanupException error)
{
    // Сохранить error.Operation (тот же объект); сообщить о неподтверждённой очистке.
    // Когда владелец решит повторить очистку, вызвать await operation.ExecuteAsync().
    // Повторная ошибка снова сохраняет владение; новый процесс никогда не запускается.
    throw;
}
```

`PrepareRunAsync` валидирует данные, сохраняет Created, фиксирует снимки и возвращает
владельца без запуска процесса ОС. Токен подготовки действует только до вставки включительно.
Возвращённую попытку нужно выполнить либо явно отменить и выполнить; простое отбрасывание
оставляет Created, а не отменённый Run. Данные исходников относятся к наблюдению при подготовке,
а не к атомарному или постоянно обновляемому снимку рабочего дерева.
`ExecuteAsync` повторно проверяет доверие/fingerprint задачи непосредственно перед первым
запуском. Токена запроса у него нет. `WaitAsync(token)` требует уже запущенного driver и
отменяет только своё ожидание. Потокобезопасный `RequestCancellation()` фиксирует намерение;
true означает, что выбрана причина отмены, включая повторные запросы. false означает, что
победила другая причина. Ни одно значение не означает сохранённый терминальный статус.

Повторные/одновременные вызовы `ExecuteAsync` возвращают ту же задачу driver. Только
наблюдённый `ProcessCleanupException` разрешает новый вызов driver с продолжением очистки
через тот же дескриптор исполнения. `StartRunAsync` остаётся сокращением с ожиданием всего
сценария; его токен не останавливает исполнение после вставки. При ошибке очистки свойство
`Operation` исключения предоставляет сохранённого владельца Application. Прямые потребители
Execution сохраняют `ProcessCleanupException.Execution`. Обычные исключения исполнения
допустимы только после подтверждённой очистки; Application сохраняет Failed с безопасной
обобщённой диагностикой.

## Арбитраж и основания терминального статуса

Блокировка отдельной попытки сериализует старт, выбор отмены и deadline. Первая принятая
причина окончательна. Перед поздним cancel/deadline проверяется завершение: на Windows
требуются root exit/code и пустой собственный Job, поэтому при живых потомках отмена
остаётся возможной. Non-Windows проверяет root exit. Принятый до завершения запрос управления
не меняет причину после выхода. Повторы и поздние таймеры не выбирают другую причину.
См. [свидетельства завершения Windows-группы](windows-group-lifecycle.ru.md).
Подтверждение старта сохраняется как Running до терминального обновления; управление может
прийти во время подтверждения, но обработка терминального результата ждёт его завершения.

- Отмена до старта ОС даёт Created → Canceled, без PID и логов.
- Отмена с подтверждённым завершением исполнения и успешным сбором даёт Canceled.
- Deadline с подтверждённым завершением исполнения и успешным сбором даёт TimedOut.
- Естественный exit zero и завершённый сбор дают Succeeded; ненулевой exit даёт Failed.
- Критическая ошибка сбора даёт Failed, даже если остановку инициировали cancel/deadline.
- Неподтверждённая остановка/очистка даёт исключение **без терминальной записи**. Running
  остаётся Running (либо Created остаётся Created, если запись Running не удалась).

В Application один путь завершения и одно терминальное сохранение с последней сохранённой
версией; store по-прежнему проверяет оптимистическую конкуренцию. Domain сохраняет финальность
терминальных состояний и отсутствие exit code у Canceled/TimedOut. При ошибке сохранения
подтверждения старта принадлежащий процесс останавливается до передачи исходной ошибки.
Если остановка тоже не удалась, сначала возвращается ошибка очистки с сохранённым владельцем;
после успешной повторной очистки передаётся исходная ошибка хранения без выдуманной
терминальной записи. Ошибки терминального сохранения передаются вызывающему без автоматического
повтора или переклассификации.

## Границы очистки и ограничения

На Windows Execution вызывает `TerminateJobObject` и подтверждает root exit плюс нулевой
Job accounting, закрывая root handle после сохранения exit code. Non-Windows сохраняет
`Kill(entireProcessTree: true)` и подтверждение root exit. Подтверждение принудительной очистки
и затем оба drains отдельно ограничены пятью секундами. Отказ остановки без подтверждения,
недоступные групповые свидетельства или истечение ожидания дают `ProcessCleanupException`.
Дескрипторы, незавершённый ввод-вывод, выбранная причина и ошибка подтверждения остаются у
того же владельца. Таймаут чтения отменяет ожидающие чтения/записи и закрывает читающие
каналы; повтор проверяет завершение ввода-вывода с тем же ограничением. Неограниченного
резервного ожидания нет. Ограничения относятся к асинхронным ожиданиям, а не длительности
системного kill, закрытия файловой системы или callback БД Application. Автоматического
цикла повторов или worker нет.

Основание Windows-остановки — **root exit/code, ноль активных процессов Job и завершённый
сбор**; для Canceled/TimedOut сбор должен быть успешен. Потерю Job нельзя исправлять по EOF
или сохранённым PID. Non-Windows по-прежнему подтверждает лишь root exit и завершённый сбор;
best-effort .NET tree kill не доказывает остановку потомков после root exit. Ни один backend
не является security sandbox. Хост обязан сохранять
владение и явно разрешать ошибки очистки; отмена запроса никогда не освобождает владельца
и не отменяет обязательную запись статуса. [Локальное recovery M3.3](run-recovery.ru.md)
теперь фиксирует подтверждённую потерю владельца как Interrupted, включая неоднозначный
старт Created. Оно не подтверждает и не выполняет остановку осиротевших детей.

Тесты используют реальные синтетические процессы и SQLite. Проверяются отмена ожидания с
сохранением владельца живого процесса, отмена долгого процесса, поздняя отмена после
естественного выхода, оба порядка и одновременная гонка cancel/deadline, повторные запросы
отмены/driver, запрет остановки с повторной очисткой, ошибка подтверждения вместе с запретом
остановки, отмена до старта, повторная проверка доверия и единственная терминальная версия.
Управляемый TimeProvider делает гонки deadline детерминированными, не выдумывая свидетельства
выхода процесса. Существующие тесты также покрывают настоящий timeout/очистку дерева, лимиты
вывода, ошибки сохранения и сбор потоков. Проверена Windows; Unix здесь не проверен.
